# PRD: Payload size & depth limits

> Every request is measured before any handler parses it — body bytes, JSON nesting depth, array length, total keys, string length, URL length — against limits sized to the plan tier and tightenable per org. Oversized or over-nested requests are refused with a 413/414/422 whose body names the dimension, the measured value, the limit, and the fix (down to a chunking plan), and a console lets a developer pre-check any payload against the exact same rules.

**Status:** Built (prototype is the spec) · **Roadmap:** F-314 · **Routes:** `/console/payload-limits`, `GET|PATCH /v1/limits/payload`, `POST /v1/limits/payload/check`, enforcement on every `/api/v1/*` request, `X-Payload-Limit-*` on every response
**Owner:** Product · **Last updated:** 2026-09-07

> Reverse-engineered from the shipped prototype for the engineering-to-scale handoff.

## 1. Context & Problem
The gateway inspected bodies for attack signatures (WAF, F-303) and validated parameters (F-079), but nothing bounded a request's *shape*: a 50 MB batch or a 100k-deep JSON nest reached the parser. That is both an abuse vector (memory exhaustion, parser recursion) and a developer-experience hole — the incumbents' answer is an opaque 413 with no hint of what to change. F-314 adds the bound and makes it self-explanatory: limits are visible on every response, enforced identically at the edge and in a console analyzer, and every rejection tells the developer exactly how to fix it.

## 2. Goals & Non-Goals
**Goals**
- **Six dimensions, one model:** body bytes (UTF-8), nesting depth, longest array, total keys, longest string, URL length — with per-tier ceilings (Starter 256 KB / 16 / 500 / 2,000 / 8 KB / 4 KB; Growth 1 MB / 24 / 2,000 / 10,000 / 32 KB / 8 KB; Enterprise 4 MB / 32 / 10,000 / 50,000 / 128 KB / 8 KB) off the same throughput-tier ladder the rate limiter uses. Sandbox keys are Starter.
- **Real enforcement, first in the pipeline:** measured from a cloned body before any sub-router parses it; rejected with `413 PAYLOAD_TOO_LARGE`, `414 URI_TOO_LONG`, or `422 PAYLOAD_TOO_DEEP | PAYLOAD_ARRAY_TOO_LONG | PAYLOAD_TOO_MANY_KEYS | PAYLOAD_STRING_TOO_LONG`. The error carries `details { dimension, measured, limit, tier, fix, violations[], docs }`.
- **Limits that explain themselves:** every fix is concrete — a chunk plan ("send 3 requests of ≤400 items"), "use `?fields=`", "submit as an async job (POST /v1/jobs)", "flatten the payload", "move identifiers into a POST body" — plus the next plan that would accept the payload.
- **Escape hatches stay open:** ingest endpoints carry a per-endpoint profile on every plan — `POST /v1/jobs` accepts up to 10,000 inputs / 4 MB (matching the job engine's own cap) and `/v1/enrich/stream` 500 inputs (matching the stream engine) — so "submit it as a job" is always a real way out, and the pre-existing `JOB_TOO_LARGE` / `STREAM_TOO_LARGE` checks stay reachable and consistent.
- **Advertised:** `X-Payload-Limit-Bytes` / `X-Payload-Limit-Depth` on every gateway response (not on the Edge middleware's 401/429), CORS-exposed.
- **Pre-checkable:** a console analyzer running the identical SSOT, and a free gateway dry run (`POST /v1/limits/payload/check`) that measures without executing or recording.
- **Enterprise control:** an admin tightens any dimension for the org (the plan ceiling is the hard maximum; never below the smallest preset). **The gateway is the writer of record** — `PATCH /v1/limits/payload` is a first-class admin API (Explorer/CLI-usable); the console adopts the gateway's overrides on load and mirrors each edit with a PATCH, cached per org handle so tenants never leak into each other. A per-org rejection ledger with 24h stats; every rejection is also written to the gateway request log.
- **Stack-safe and deterministic:** iterative measurement (an explicit stack, early exit); no `Math.random`; fully unit-tested.

**Non-Goals (this phase)** — aborting a streaming upload at byte N before the body is buffered (the prototype reads a clone; production should stream-count and abort); customer-defined per-endpoint limits (only the two built-in ingest profiles exist; overrides are one set per org); header-size / header-count limits; multipart/form bodies; raising limits above the plan ceiling by support ticket; a tenant-store schema change (overrides live in their own persisted store).

## 3. Users & Personas
- **Integrating developer (land):** the 422 they hit at 11pm says "Array length is 1,200 items; the limit for your Starter plan is 500 items. Send 3 requests of ≤400 items each, or submit the whole set as one async job (POST /v1/jobs). The Growth plan raises this limit to 2,000 items." They paste the body into the analyzer and see the same meters.
- **Platform lead (expand):** watches the rejection ledger to catch a runaway integration, tightens limits below the plan for a noisy team.
- **Security officer (expand):** sees the parser-abuse surface bounded and advertised, with depth and key-count limits, not just bytes.
- **RBAC:** page viewable by `admin | developer`; **limit overrides and reset are admin-only** (read-only badges for developers). Analyzer, dry run and send-for-real available to both.

## 4. Differentiation
Table-stakes protection with a DX twist, tied to **win #6 (enterprise-grade security)** and the DX bar. Stripe returns a clear 413 but nothing configurable; AWS API Gateway has an opaque 10 MB ceiling; Cloudflare gates body size by plan. None measure depth/array/key dimensions, none explain the fix, and none let you pre-check. Ours: limits are visible, pre-checkable, and self-explaining — the analyzer's prediction *is* the edge's verdict because they run the same module.

## 5. Data Model & Logic
Single source of truth: **`lib/payload-limits.ts`** (pure helpers + a dedicated persisted store).
- Types: `PayloadLimits`, `PayloadOverrides`, `PayloadMeasure`, `PayloadViolation` (with `code`, `status`, `message`, `fix`), `PayloadVerdict`, `DimensionSpec`, `SamplePayload` (no `any`).
- Catalog: `DIMENSIONS` (ordered by severity: bytes → depth → array → keys → string → URL; each with its code, status and admin presets), `TIER_PAYLOAD_LIMITS`, `tierThatFits`, `ENDPOINT_PROFILES` + `profileForPath` + `resolveLimitsForPath` (the ingest escape hatches).
- Limits: `resolveLimits(tier, overrides)` (tighten-only, clamped to the ceiling, floored at the smallest preset), `normalizeOverrides(unknown)` (numeric known keys; `null` clears; drops, never throws).
- Measurement: `utf8ByteLength` (runtime-independent), `measureJson(root, stopAtDepth)` (iterative), `measurePayload(raw, url, opts)` (invalid JSON → bytes/URL only; the gateway passes `skipParseAboveBytes` + `stopAtDepth` so an oversized body is never fully parsed just to be refused).
- Verdict: `evaluatePayload(measure, limits, tier)` → every violated dimension with a fix, `chunkPlan`, `formatBytes`/`formatMeasure`, `utilisation`, `payloadLimitHeaders`.
- Samples: `SAMPLE_PAYLOADS` — five deterministic analyzer presets (healthy 200-batch, 1,200-batch, 40-deep nest, 300 KB notes field, unicode-heavy names).
- **`usePayloadLimits`** — Zustand store persisted under its own key (`zinbit-payload-limits`), separate from the tenant store. A per-org **cache** of the gateway's overrides: `byOrg: Record<orgHandle, PayloadOverrides>`; actions `adopt(orgId, overrides)` (from GET), `setLimit(orgId, key, value | null)`, `reset(orgId)`; `overridesForOrg` selector. Cleared by Reset Demo Data.

## 6. State / Integration
- **Gateway module** [`src/lib/gateway/payloadLimits.ts`](../../src/lib/gateway/payloadLimits.ts): `limitsForKey` (org handle via `orgHandleForKey`, tier via `tierForKey`), `guardPayload` (measure + judge + record; GET/HEAD judged on URL only), `attachPayloadLimitHeaders`, `dryRunPayload` (no side effects), `getPayloadLimitsSnapshot` (limits, ceiling, overrides, ledger of 50, stats), `updatePayloadOverrides`, `__resetPayloadLimits`. Per-org ledger (cap 200) seeded deterministically so it reads as a running system.
- **Pipeline** [`route.ts`](../../app/api/v1/[...route]/route.ts): after the CORS preflight return and before every sub-router — the `/v1/limits/payload*` meta routes first (so the dry run can *measure* an oversized body rather than be rejected by it), then the guard on everything else, reading `request.clone().text()` so downstream `request.json()` still works. A rejection is `logRequest`-ed like any terminal status and carries `details.docs` as an absolute console URL (from `lib/api-config.ts`). The Edge middleware has already spent a rate-limit token on a rejected request (same as a WAF 406). Headers attached on every gateway response. An unparseable body is judged on bytes/URL and then treated by the pipeline as an empty body (the endpoint's parameter validation decides).
- **CORS** exposes `X-Payload-Limit-Bytes` / `X-Payload-Limit-Depth`. **Insight engine** `explainStatus` now explains 413 (plan body cap *or* an endpoint input cap), 414 and 422 (RCA narratives + ticket triage), and `explainMatch` classifies 413/414/422 as "payload over a limit" (excluded from match rate) separately from 400 validation.
- **Catalog** entry `payload-limits` in [`endpoints.ts`](../../src/data/endpoints.ts) → docs/Explorer/OpenAPI/Postman/CLI; next steps point to the console and to async jobs.
- **Console** `/console/payload-limits`: nav "Payload Limits" beside the WAF (admin, developer). Reads `GET /v1/limits/payload` on load and adopts its overrides (server authoritative); each edit PATCHes one key (reset PATCHes all six as `null`) then re-reads; dry run via `POST /check`; send-for-real via `POST /v1/batch/enrich` then refreshes the ledger. Lists the endpoint profiles under the limits. Cross-links: Security Hub, WAF, Logs, Explorer deep link, Jobs.

## 7. UI states
Composed from `components/ui` (PageHeader, KpiTile, GlassCard, Button, ConfirmAction, StatusBadge, DataTable, EmptyState, Skeleton). **Loading** — KPI tiles in `loading` + block skeletons mirroring the three cards. **Limits** — six dimension rows (icon, effective value, ceiling or code); admin `<select>` of presets ≤ ceiling + "Plan default"; tightened rows tinted; "Reset to plan defaults" behind a confirm. **Analyzer** — sample chips (`aria-pressed`), a 2 MB-capped textarea with clear, per-dimension meters (`role="meter"`, spring-animated, teal / warning ≥80% / error >100%, n/a for structure when not JSON), a verdict panel (green "within every limit", or one red card per violation with code, message, fix and chunk plan), a dismissible **upgrade nudge** only when the *plan* — not an override — is the blocker, and a probe result panel (dry run or real; HTTP status + code + the limit headers) with an error-toned panel + Retry when the gateway is unreachable. **Ledger** — sortable, paginated table (time, request, dimension, measured/limit, response); empty state; skeleton; error + retry; a no-key empty state. Semantic tokens only; light + dark; staggered section entrances.

## 8. Telemetry
Via `lib/telemetry.ts`: `payload_limits_viewed` (tier), `payload_analyzed` (ok, violations, primary, bytes, source — debounced), `payload_probe_sent` (mode dry|real, status, code), `payload_limit_changed` (limit, value), `payload_limits_reset`, `payload_upgrade_clicked` (from, to, dimension). Emitted from the console.
