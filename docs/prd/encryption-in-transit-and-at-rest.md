# PRD: Encryption in transit & at rest

> The crypto guarantee, made inspectable: a live, HMAC-signed attestation of how data is protected on the wire (TLS 1.3 + cipher, HSTS, PFS) and at rest (AES-256-GCM envelope encryption, customer-managed KMS keys, rotation schedule, field-level PII), pullable and verifiable in one API call and manageable from the console — with the console and the gateway guaranteed to agree.

**Status:** Built (prototype is the spec) · **Roadmap:** F-312 · **Routes:** `/console/encryption`, `GET|PATCH|POST /v1/encryption`, `GET /v1/encryption/verify`, `X-Encryption-*` on every `/api/v1/*` response
**Owner:** Product · **Last updated:** 2026-09-07

> Reverse-engineered from the shipped prototype for the engineering-to-scale handoff.

## 1. Context & Problem
The gateway already enforced TLS-in-transit and set HSTS/CSP headers ([security.ts](../../src/lib/gateway/security.ts)), but that guarantee was invisible and there was nothing for **at-rest**: no key inventory, no rotation, no field-level PII story. Enterprise security reviews ask for both, in writing, and they probe the word "signed". F-312 turns "we encrypt everything" into something a developer can *see, pull, and verify* — a live posture endpoint whose attestation the gateway signs, and a console that inspects transit, manages the KMS keys that wrap data at rest, and stays in lock-step with the endpoint.

## 2. Goals & Non-Goals
**Goals**
- **In transit, visible:** the negotiated TLS version + cipher + key exchange, HSTS, forward secrecy, OCSP stapling — and `X-Encryption-Transit`/`X-Encryption-Rest` headers on **every** API response, CORS-exposed so browser clients can read them. HSTS on the wire is derived from the same posture model.
- **At rest, managed:** an AES-256-GCM envelope model — a customer-managed KMS key per purpose (data/PII/backups/exports), an encrypted-store inventory, a rotation schedule, and admin-driven **rotate now** + cadence.
- **Field-level PII encryption:** deterministic (searchable) vs randomized (always-on) modes, admin-tunable; the randomized floor is enforced in the shared model, not only the UI. Applies to `sk_live_` traffic; sandbox returns synthetic data (mirrors masking).
- **One-call, verifiable attestation:** `GET /v1/encryption` returns a stable digest + posture score, **HMAC-SHA256-signed** by the gateway (`alg`, `kid`, `sig`, `issuedAt`); `GET /v1/encryption/verify` checks a digest + signature pair.
- **Console ↔ gateway coherence:** the console syncs its persisted settings to the gateway over `PATCH /v1/encryption` on mount and on every change, so both compute the same score and digest; the live check shows when they differ.
- **Deterministic** everything (FNV, injected `now`) — no `Math.random`, fully unit-tested.

**Non-Goals (this phase)** — real cryptographic key material or a real KMS/HSM integration (fingerprints/digests are non-secret display artifacts); actually re-encrypting stored bytes on rotation (envelope re-wrap only); BYOK/HYOK upload; certificate/TLS-cert management; per-tenant HSTS config; asymmetric (public-key) attestation signatures a third party could verify offline (the HMAC is verifiable against the issuing gateway); feeding rotation events into the audit log; a tenant-store schema change (settings live in their own persisted store).

## 3. Users & Personas
- **Developer (land):** hits `/v1/encryption` and gets a machine-readable, signed attestation to drop into a security questionnaire; sees the `X-Encryption-*` headers on their own traffic in seconds; verifies any pair at `/v1/encryption/verify`.
- **Security/IT admin (expand):** owns the KMS rotation cadence, rotates on demand, and sets field-level PII encryption — the enterprise checkbox for SOC2/vendor reviews. The Security Hub shows the posture at a glance.
- **RBAC:** page viewable by `admin | developer | billing`; **rotation, cadence, and field toggles are admin-only** (read-only list for others). Live check + attestation copy are available to all viewers.

## 4. Differentiation
Ties to **win #6 (enterprise-grade security)**. Competitors (Stripe/AWS) bury encryption posture in static compliance PDFs; nobody gives developers a **live, self-serve encryption posture endpoint + console with a pullable, verifiable signed attestation**. The depth is that transit is *proven on the wire* (real response headers, a live check), at-rest is *operable* (real KMS rotation that visibly moves the schedule), and the two surfaces *cannot disagree* (settings sync + a visible mismatch state).

## 5. Data Model & Logic
Single source of truth: **`lib/encryption.ts`** (pure helpers + a dedicated persisted store).
- Types: `TlsPosture`, `KmsKey`, `EncryptedStore`, `FieldEncryption`, `EncryptionPosture`, `EncryptionSettingsPatch` (no `any`).
- Deterministic derivation: `fnv`/`fingerprint` (non-secret), `orgHandleForKey` (the one org handle both console and gateway use; no key → `org_demo`), `TLS_POSTURE` (TLS 1.3 / `TLS_AES_256_GCM_SHA384` / X25519 / HSTS-preload 730d), `hstsHeaderValue` (the exact `Strict-Transport-Security` value the gateway serves), `deriveKeys` (per-purpose KMS keys; primary follows cadence + `lastRotatedAt`), `deriveStores`, `deriveFields` (randomized fields always `enabled`), `isFieldRelaxable`, `normalizeSettingsPatch` (narrows an untrusted body: cadence allowlist, boolean toggles, known deterministic fields only — drops, never throws), `postureScore` (transit 35 + store coverage 30 + PII coverage 20 + rotation freshness 15), `attest` (digest over **material** facts only — independent of rotation timestamp), `buildPosture`, `daysUntilRotation`.
- **`useEncryptionSettings`** — Zustand store persisted under its own key (`zinbit-encryption`), separate from the tenant store (like `useMfaPolicy`/`useLoginGuard`). State: `rotationDays`, `lastRotatedAt`, `fieldEncryption`. Actions: `setRotationCadence` (allowlisted 30/60/90/180/365), `rotatePrimaryKey`, `setFieldEncryption` (ignores non-relaxable fields), `reset`.

## 6. State / Integration
- **Gateway meta module** [`src/lib/gateway/encryption.ts`](../../src/lib/gateway/encryption.ts): `attachEncryptionHeaders` (beside `attachISO27001Headers`; `kx=X25519; pfs=ECDHE`; live keys advertise `pii=field-level`), `ENCRYPTION_EXPOSED_HEADERS`, `signAttestation`/`verifyAttestation` (HMAC-SHA256 over `${orgId}.${attestation}`, secret from `ZINBIT_ATTESTATION_SECRET` with a prototype default, `kid = zinbit-attest-2026-09`), `getEncryptionPosture` (org-scoped, signed, per-org settings), `updateEncryptionSettings` (PATCH), `runRotationDrill` (envelope re-wrap), `__resetEncryption`.
- **Real endpoint** `/v1/encryption` wired into [`route.ts`](../../app/api/v1/[...route]/route.ts) before route resolution/billing: `GET` = signed posture, `PATCH` = settings sync (400 on a non-object body), `POST` = rotate, `GET /v1/encryption/verify?attestation=&sig=` = `{ valid, orgId, kid }` (400 when either param is missing), else 405. `creditCost: 0`. Catalog entry in [`endpoints.ts`](../../src/data/endpoints.ts) → feeds docs/Explorer/OpenAPI/Postman/CLI.
- **CORS** [`cors.ts`](../../src/lib/gateway/cors.ts): `EXPOSED_RESPONSE_HEADERS` (`Access-Control-Expose-Headers`) now lists the request-id, credits, rate-limit, and `X-Encryption-*` headers. **HSTS** in `security.ts` is `hstsHeaderValue()` from the SSOT.
- **Console** `/console/encryption`: reuses `authHeaderValue` + `activeKeys`; `orgHandleForKey` for the handle; a `PATCH` sync effect on mount/env/key/setting change; a real same-origin live check (`GET`) that renders the wire headers and the gateway's signature; rotation `POST`s. Nav entry (role-filtered), cross-links to Security Hub / Keys / Logs / Explorer.
- **Inbound links:** the Security Hub ([`app/console/security/page.tsx`](../../app/console/security/page.tsx)) shows an Encryption card (score, TLS version, KMS keys, next rotation) linking to the console; Settings → Security → Data & Privacy links to it. **Reset Demo Data** (Settings → Profile) clears `zinbit-encryption`, `zinbit-mfa-policy`, and `zinbit-login-guard` alongside the tenant store.

## 7. UI states
Composed from `components/ui` (PageHeader, KpiTile, GlassCard, DataTable, SegmentedControl, ConfirmAction, StatusBadge, Skeleton, Button). **Loading** — KPI tiles in `loading` + block skeletons mirroring each section (no layout shift). **No key** — posture still renders ("encryption is always on") with an inline create-a-key callout; live check disabled with a reason. **Ready** — transit inspector (+ live header reveal via Framer Motion), KMS key table (sorted by next rotation, overdue in red), encrypted-store table, PII field grid (`aria-pressed` toggles with focus rings for admins; a plain list for others; a live/sandbox badge), attestation card (digest; after a live check a "Signed · HMAC-SHA256" badge, truncated signature, Copy digest / Copy signature with a "Copied" label swap). **Mismatch** — a warning badge when the gateway digest differs from the console's. **Error** — live-check failure renders an error-toned panel with the HTTP status + message and a Retry button (never a placeholder in the success panel). **Non-admin** — cadence/rotate/toggles read-only. Semantic tokens only; light + dark; staggered section entrances.

## 8. Telemetry
Via `lib/telemetry.ts`: `encryption_viewed`, `encryption_checked` (live check, with `ok` + `status`), `encryption_key_rotated` (with cadence), `encryption_field_toggled` (field + enabled), `encryption_cadence_changed` (from → to). Emitted from the console.

## 9. Verification

## 10. Deferred
Real KMS/HSM + BYOK/HYOK; asymmetric attestation signatures (Ed25519 + a public JWKS) for offline third-party verification; actual byte-level re-encryption on rotation; TLS certificate management; per-tenant HSTS; audit-log entries for rotation/policy changes; org-scoped (rather than key-suffix-scoped) settings across tenants; export-specific PGP encryption (F-463); API-key-hashed-at-rest surfacing (F-321) cross-link.
